In Kubernetes, a controller is a core component that continuously watches the current state of the cluster and compares it with the desired state defined by the user in YAML files. If there is any difference between the current state and desired state, the controller automatically takes action to make them match. Kubernetes works on the concept called “desired state management.” This means the user tells Kubernetes what they want, and Kubernetes controllers make sure that state is maintained all the time.

For example, if you create a Deployment and mention that you need 3 replicas of an application pod, the Deployment Controller continuously checks whether exactly 3 pods are running or not. If one pod crashes or gets deleted, the controller automatically creates another pod to maintain the required count. If you increase replicas from 3 to 5, the controller creates 2 more pods automatically. If you reduce replicas from 5 to 2, the controller removes extra pods. This automatic monitoring and correction is the main responsibility of controllers.

A controller mainly works in a loop called the reconciliation loop. In simple words, the controller repeatedly performs three activities. First, it watches the cluster state using the Kubernetes API Server. Second, it compares the actual state with the desired state. Third, it performs corrective actions if both states are different. This process runs continuously in the background.

Kubernetes has many built-in controllers, and each controller handles a specific resource or task. The Deployment Controller manages Deployments and ensures the correct number of pods are running. The ReplicaSet Controller maintains the required replica count. The Node Controller monitors worker nodes and checks whether nodes are healthy or not. The Job Controller manages batch jobs and ensures tasks complete successfully. The StatefulSet Controller manages stateful applications like databases where pod identity and storage persistence are important. The DaemonSet Controller ensures one pod runs on every node, commonly used for monitoring or logging agents.

For example, suppose a node becomes unhealthy or disconnected from the cluster. The Node Controller detects this issue and marks the node as “Not Ready.” Then Kubernetes may reschedule pods to another healthy node. Similarly, if a pod enters a failed state, the ReplicaSet Controller immediately creates a new pod. Because of controllers, Kubernetes becomes self-healing and automated.

The controller itself does not directly run containers. Instead, it interacts with the API Server. The API Server stores cluster information in etcd, which is the Kubernetes database. The controller reads resource information from the API Server and updates resources through the API Server. So the controller acts like a manager that continuously checks and fixes cluster resources.

Now coming to Operators, an Operator is an advanced form of a Kubernetes controller. Operators are specially designed to automate complex application management tasks that normal controllers cannot handle easily. Operators extend Kubernetes functionality using custom logic and domain knowledge.

A normal controller mainly manages Kubernetes resources like pods, replicas, and nodes. But Operators manage complete applications such as databases, monitoring systems, message queues, or enterprise applications. Operators understand how the application works internally and can automate operational tasks like installation, upgrades, scaling, backups, recovery, failover, and configuration management.

For example, managing a MySQL database manually in Kubernetes can become difficult because databases require backup handling, replication setup, failover management, storage configuration, and version upgrades. A MySQL Operator automates all these activities. The operator knows how MySQL behaves and performs database-specific operations automatically.

An Operator mainly consists of two important things called Custom Resource Definition (CRD) and Custom Controller. CRD allows users to create their own Kubernetes resource types. Normally Kubernetes has built-in resources like Pod, Service, and Deployment. But using CRD, we can create custom resources like MySQL, KafkaCluster, RedisCluster, or Prometheus.

For example, after installing a MySQL Operator, you can create a YAML like this:

```yaml
apiVersion: database.example.com/v1
kind: MySQL
metadata:
  name: mydb
spec:
  replicas: 3
  version: 8.0
```

Here, “MySQL” is not a default Kubernetes resource. It is a custom resource created by the Operator using CRD. The Operator watches this custom resource and automatically creates StatefulSets, Services, Persistent Volumes, backups, replication setup, and monitoring configuration required for MySQL.

The Operator continuously monitors the database state similar to normal controllers, but it also contains application intelligence. If the primary database fails, the Operator may automatically promote a replica as the new primary database. If a version upgrade is required, the Operator performs rolling upgrades safely. If backup schedules are configured, the Operator handles them automatically.

In simple words, you can think like this:

A normal Kubernetes controller manages infrastructure-level resources and keeps the cluster state correct.

An Operator manages complete applications and contains expert knowledge about that application.

For example, Deployment Controller only ensures pods are running. But a MongoDB Operator knows how to create MongoDB clusters, handle replication, perform backup and restore, manage scaling, recover failed nodes, and upgrade database versions safely.

Controllers are built into Kubernetes and mainly focus on generic resource management. Operators are usually created using tools like Operator SDK or Kubebuilder and are mostly used for complex stateful applications.

The relationship between controller and operator is very important. Every Operator internally uses a controller pattern. This means an Operator is basically a custom controller with additional application-specific intelligence and automation logic.

If we compare them simply:

A Controller says, “Make sure this resource stays in the desired state.”

An Operator says, “I know how this application works, so I will fully manage its lifecycle automatically.”

For DevOps engineers, controllers are important because almost every Kubernetes object depends on controllers internally. Operators are important because modern cloud-native applications increasingly use Operators for automating complex systems like databases, monitoring stacks, CI/CD tools, and messaging systems.

Popular examples of Operators are the Prometheus Operator for monitoring setup, Elasticsearch Operator for Elasticsearch clusters, Kafka Operator for Kafka management, and MySQL or PostgreSQL Operators for database automation.

In real-time projects, controllers help Kubernetes provide self-healing, scaling, and automation, while Operators reduce manual operational work and improve reliability for complex applications.
# Controller in Kubernetes

Kubernetes Controller is a control loop that continuously monitors the cluster state and ensures the actual state matches the desired state.

Controllers automatically manage Kubernetes resources like Pods, Deployments, Nodes, Jobs, and ReplicaSets.

Controllers help Kubernetes maintain automation, self-healing, scaling, and reliability.

Controllers run inside the Kubernetes Control Plane through the Controller Manager.

## What is Desired State

Desired State is the configuration defined by the user in YAML files or Kubernetes resources.

Example, if the user defines 3 Pod replicas, Kubernetes considers 3 Pods as the desired state.

## What is Actual State

Actual State is the current running condition inside the cluster.

Example, only 2 Pods are running instead of 3.

## Controller Working Process

Controller continuously watches Kubernetes resources using API Server.

Controller compares Desired State with Actual State.

If differences exist, Controller takes corrective actions automatically.

Controller creates, deletes, or updates resources to match desired state.

## Real-Time Example

User creates Deployment with 3 replicas.

Deployment Controller creates ReplicaSet.

ReplicaSet Controller creates 3 Pods.

If one Pod crashes, ReplicaSet Controller detects missing Pod.

Controller automatically creates a new Pod.

Cluster again reaches desired state of 3 running Pods.

## Controller Manager

Kubernetes Controller Manager runs multiple controllers together.

Controller Manager continuously monitors cluster resources.

Controller Manager communicates with API Server and ETCD.

## Types of Kubernetes Controllers

Kubernetes contains multiple specialized controllers for different tasks.

## Deployment Controller

Deployment Controller manages Deployments and ReplicaSets.

Deployment Controller handles rolling updates and rollback functionality.

Deployment Controller ensures required Pod replicas are running.

Example:

```yaml id="jlwm1a"
replicas: 3
```

If Pods fail, Deployment Controller recreates them automatically.

## ReplicaSet Controller

ReplicaSet Controller ensures specified number of Pod replicas are always running.

If a Pod fails, ReplicaSet Controller creates replacement Pods automatically.

## Replication Controller

Replication Controller is an older controller used before ReplicaSets.

ReplicaSets are modern replacements for Replication Controllers.

## StatefulSet Controller

StatefulSet Controller manages stateful applications like databases.

StatefulSet provides stable Pod names and persistent storage.

Stateful applications require ordered deployment and stable identities.

Examples are MySQL, PostgreSQL, and MongoDB clusters.

## DaemonSet Controller

DaemonSet Controller ensures one Pod runs on every worker node.

DaemonSets are commonly used for monitoring agents, logging agents, and networking services.

Example use cases are Prometheus Node Exporter and Fluentd log collectors.

## Job Controller

Job Controller manages batch jobs and one-time tasks.

Job Controller ensures tasks complete successfully.

After successful completion, Pods stop automatically.

Example use cases are backups and database migrations.

## CronJob Controller

CronJob Controller schedules Jobs periodically based on time schedules.

CronJobs work similarly to Linux cron jobs.

Example schedule:

```yaml id="’wini2b"
schedule: "0 2 * * *"
```

This example runs job daily at 2 AM.

## Node Controller

Node Controller monitors worker node health and availability.

If a node becomes unreachable, Node Controller updates cluster status.

Node Controller may reschedule Pods to healthy nodes.

## Namespace Controller

Namespace Controller manages Namespace lifecycle and cleanup operations.

## Service Account Controller

Service Account Controller creates default service accounts for namespaces automatically.

## Endpoint Controller

Endpoint Controller updates Service endpoints dynamically when Pods change.

Services always route traffic to healthy Pods.

## Horizontal Pod Autoscaler Controller

HPA Controller automatically scales Pod replicas based on CPU or memory usage.

HPA Controller works with Metrics Server.

## Vertical Pod Autoscaler Controller

VPA Controller adjusts CPU and memory resources for Pods automatically.

## Ingress Controller

Ingress Controller manages external HTTP and HTTPS traffic routing into Kubernetes cluster.

Common ingress controllers are NGINX Ingress Controller and Traefik.

Ingress Controller configures reverse proxy rules automatically.

## Custom Controller

Developers can create Custom Controllers for application-specific automation.

Custom Controllers are commonly built using Kubernetes Operators.

## Operator Pattern

Operator extends Kubernetes functionality using custom controllers and CRDs called Custom Resource Definitions.

Operators automate complex application lifecycle management.

Examples are database operators and monitoring operators.

## Controller Communication

Controllers communicate with Kubernetes API Server continuously.

API Server stores cluster state in ETCD.

Controllers monitor resources using watch mechanisms.

Controllers update resources through API calls.

## Reconciliation Loop

Controller continuously runs reconciliation loops.

Reconciliation loop compares desired state and actual state repeatedly.

Controllers keep correcting cluster state automatically.

## Self-Healing in Kubernetes

Controllers provide self-healing functionality.

If Pods fail, controllers recreate them automatically.

If nodes fail, controllers reschedule workloads when possible.

Controllers maintain cluster reliability continuously.

## Controller Example Workflow

User applies Deployment YAML with 3 replicas.

API Server stores desired state in ETCD.

Deployment Controller detects new Deployment.

Deployment Controller creates ReplicaSet.

ReplicaSet Controller creates 3 Pods.

Scheduler assigns Pods to worker nodes.

Kubelet starts containers inside Pods.

If one Pod crashes, ReplicaSet Controller recreates missing Pod automatically.

Controllers continuously maintain desired application state.

## Advantages of Kubernetes Controllers

Controllers automate resource management.

Controllers provide self-healing and recovery.

Controllers improve scalability and reliability.

Controllers reduce manual operational work.

Controllers continuously maintain desired cluster state.

## Limitations of Controllers

Misconfigured controllers may create unexpected resource behavior.

Large clusters may require controller performance tuning.

Complex controller interactions may become difficult to troubleshoot.
